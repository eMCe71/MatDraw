# MatDraw

Responsive Polish taekwondo tournament app for MEDUCASE, with a public martial-arts chat, paid member accounts and an installable app (PWA). Brand: MatBravo (formerly MatDraw); domain `matbravo.com`. Internal identifiers (PHP namespace, cookie, storage keys, the `~/matdraw` directory) keep the `matdraw` name.

## Two runtimes

- `dist/`: self-contained Sites preview. Clearly marked demo accounts and local browser storage. Fictional athletes, role shortcuts, no shared online authentication. The demo also has a local chat (`dist/chat-demo.js`, fictional messages in the browser's `localStorage`); sign-up and payments only show a notice and there is no service worker.
- `backend/`: PHP/PDO + MySQL implementation with real sessions, password authentication, server-side role and club authorization, transaction/revision guards, rules, bracket results, schema, migrations and first-admin CLI installer. Requires deployment on PHP hosting; not executed by Sites static hosting.

The interface has multiple tournaments and one reusable athlete directory. An entry is a per-tournament snapshot: age, grade, events, registration weight, check-in and results stay isolated. Profiles can be archived without deleting history. Club representatives see only their own club. Admins provision, edit and block accounts. Editors manage tournaments and profiles they create. Registration status and finished-tournament locks are enforced on the server.

On top of the tournament workspace there are now (all switchable in `config.php`, all off or safe by default):

- **Chat.** Four global channels (Taekwondo World, Taekwondo Poland, Karate World, General) and one channel per tournament. Anyone can read; only signed-in people with full access can write. See "Chat" below.
- **Member accounts.** A new role `member` (self-service sign-up) with a profile (first and last name, user name, country, sports, optional photo). A plain member never sees the tournament workspace; a member with the organizer capability sees only their own tournaments (below).
- **Paid accounts.** 8.99 PLN or 2.99 USD per month through hosted Stripe Checkout and the Customer Portal, without the Stripe SDK, Composer or Stripe.js. Staff accounts (admin, editor, club) can be free (Admin's decision) or paid. See "Payments".
- **PWA.** Two manifests (PL, EN), a versioned service worker with offline page, install prompts after real use, update bar. See "PWA".
- **Roles for members, sign-up modes and self-entry.** A member can also be an *organizer* (own tournaments and athletes, nothing else) and/or an *athlete* (own profile, enters open tournaments by themselves). The Administrator opens or closes sign-up in the panel "Ustawienia" (stored in the database, no deploy). See "Roles, organizers and athlete self-entry" and "Sign-up modes".

The original MEDUCASE logo links to https://mdcse.com in the app, login, print and projection footers. Navy/blue/cyan follow the logo. A4/A3 previews, split large brackets and a separate projector window remain available. The PHP projection refreshes every 15 seconds and requires an active session.

## Run and package

Static demo: serve `dist/` with any static HTTP server. No build required.

```bash
npm run check                                    # node --check of every dist/*.js, dist/i18n/*.js and scripts/*.mjs
node --test tests/*.test.mjs                     # unit tests; HTTP and browser tests skip themselves without their environment
node scripts/build-php.mjs /absolute/path/matdraw-php
```

Read [INSTALL-PL.md](INSTALL-PL.md) for PHP deployment and [DEPLOY-PL.md](DEPLOY-PL.md) for the CI/CD deployment. Set document root to the release's `public/`; keep `backend/` outside web access. Set `backend/config.php` from the example (never commit secrets), create a MySQL database and run the CLI installer. The package starts empty and contains no production demo accounts. Existing browser demo data is not imported into the server.

PHP requires 8.3+, PDO MySQL and mbstring. MySQL 8.0+ or MariaDB 10.6+ with InnoDB (production runs MariaDB 10.6; CI tests MySQL 8.0 and MariaDB 10.6, local development MariaDB 10.11). Optional extensions: `curl` + `openssl` (payments), `gd` with WebP (profile photos; without WebP they are stored as JPEG, without GD there are no photos), `intl` (Unicode normalisation, falls back to plain text handling) and `exif` (photo orientation). No Composer, Node server, SMTP or cron needed at runtime (cron is optional, see `DEPLOY-PL.md`).

### Release build

`scripts/build-php.mjs` copies `dist/` to `public/`, `backend/` to `backend/` (without `config.php`), sets `runtime-config.js` to API mode, copies the documentation and finishes with `scripts/build-pwa.mjs`, which fills the service worker template (build number = hash of the shell files, precache list with SHA-256 per file, budget 1.5 MB) and writes `public/version.json`. A release that only changes `backend/` keeps the same build number, so nobody gets an update bar for it.

## Configuration

`backend/config.php` (in production a link to `~/matdraw/shared/config.php`, mode 600) must contain `app_url`, `db` and `app_key`. Every other key is optional: `matdraw_config()` merges the file over `MatDraw\Config::DEFAULTS` (`backend/src/Config.php`), so a config written before a release never produces warnings or different defaults in different files. `Config::validate()` refuses unsafe switch combinations with a generic message (HTTP 500, `Invalid billing configuration.` or `Invalid signup configuration.` in the log); nothing secret is ever logged.

| Group | Keys (defaults in `backend/config.example.php`, full table in `INSTALL-PL.md` Appendix A) |
|---|---|
| Sessions | `session_idle_seconds`, `session_max_seconds` (staff: 30 min / 12 h), `member_session_idle_seconds`, `member_session_max_seconds` (members: 14 / 30 days), `anon_session_seconds`, `session_dir` |
| Sign-up and accounts | `signup_enabled`, `signup_invite_token`, `signup_free_beta`, `support_email` (these four are only starting values until the Administrator saves "Ustawienia"), `signup_force_off` (emergency ceiling), `signup_limit_*`, `username_check_limit_*`, `login_limit_ip`, `abandoned_member_days`, `uploads_dir`, `avatars_enabled` |
| Chat and clients | `chat_force_off`, `min_client_api`, `trusted_proxy_header`, `trusted_proxies` |
| Payments | `billing_enabled`, `billing_enforce`, `billing_mode`, `stripe_*`, `billing_*` |
| Database | `db_migrate` (separate credentials with DDL rights, used only by `bin/migrate.php`) |
| Tests only | `job_test_sleep_ms` |

Switch matrix of the *file* (plan section 6.10; `Config::validate()` refuses the other combinations): `billing_enforce` needs `billing_enabled`; sign-up (also an invite token) needs a valid `support_email`; open sign-up needs `billing_enforce=true` (or an explicit `signup_free_beta=true` with billing off); an invite token with sign-up off needs `billing_enforce=true`. What is *in force* is computed by `Settings::effective()` from the file plus the database row (see "Sign-up modes"); `billing_enabled` only makes Stripe available, payments are required while the effective `billing_enforce` is true. The production `config.php` needs no change for this release.

Flag files in `~/matdraw/shared/` act without a deploy: `chat-off` (every chat route answers 503 `chat_off` before the database is touched) and `maintenance` (the API answers 503 "Trwa przerwa techniczna" before the database is touched; used while restoring a backup). Chat pace, the chat switch and the notice are changed from the Admin's moderation page and are stored in the database (`chat_settings`), so they also need no deploy.

## Languages (PL / EN)

- The interface is available in Polish and English. On the first visit the browser's preferred language decides (`navigator.languages[0]`, else `navigator.language`): Polish (`pl`, `pl-PL`, …) gives PL, anything else EN. The PL | EN switcher in the top bar and on the login screen re-renders the current view (filters, search, typed login data are kept) and remembers the choice in `localStorage` (`matdraw.language`), which then wins over detection. Other open windows, such as the hall screen, follow the change. `dist/lang-boot.js` sets `<html lang>` before the first paint (a classic script, so the CSP needs no inline code) and, in API mode, points the manifest link at the English manifest when the language is English.
- Gettext style: the Polish text in the code is both the key and the Polish output, e.g. `T('{n} klubów',{n})` in `dist/app.js`. English lives in dictionaries: `dist/i18n-en.js` (the original app) and one file per feature in `dist/i18n/*-en.js` (accounts, athlete, billing, chat, home, members, moderation, organizer, pwa, settings, shell) and one per server message group (`server-accounts-en.js`, `server-athletes-en.js`, `server-domain-en.js`, `server-settings-en.js`); `dist/i18n.js` merges them. A value is a string with the same `{placeholders}`, or `{one,other}` for counts. A missing entry falls back to Polish, so the Polish interface does not depend on the dictionaries. **A Polish key may appear in only one dictionary**: a key in two files is a collision and fails the test.
- Data and the API stay Polish. Rule-engine labels (events, age groups, sex, weight/height classes, grade bands), server (PHP) error messages, demo-adapter messages and stored activity entries are translated only when displayed (`ruleLabel`, `ruleText`, `translateMessage` in `dist/i18n.js`); an unknown message is shown unchanged. PHP, `engine.js` and category ids are unchanged, so JS/PHP parity is unaffected.
- Dates and decimal numbers use `pl-PL` / `en-GB`; times stay in Europe/Warsaw. User data (names, clubs, tournament names, mat names, chat messages) is not translated. Category codes (UF-01, LC-02, …) are identifiers and are the same in both languages.
- English taekwondo terms follow ITF usage: Patterns (układy formalne), sparring (walki), Special techniques, Power test, Gup (Polish "Cup") and Dan.
- To add or change text: write it as `T('Polski tekst')`, add `'Polski tekst':'English text'` to the dictionary of your feature (`dist/i18n/<feature>-en.js`), then run `node --test tests/i18n.test.mjs`. The test fails for a key without an English entry, a key present in more than one dictionary, mismatched placeholders, Polish letters in English text, Polish text in `app.js` and the feature modules outside `T()`, and any PHP, demo-adapter or rules-engine message without a translation, so a new server message needs an English entry too.
- `dist/architecture.html` contains both languages (`.only-pl` / `.only-en` blocks) and has its own switcher.

## Public schedule and guest preview

The login screen lists **upcoming tournaments** (nearest first). Picking one opens a sponsor pop-up (an advertisement); only closing it opens a **read-only guest preview** of that tournament. Guests cannot write anything: the preview has no forms, the browser accepts only navigation actions without a session, and the server has no public write route. The list sits beside the headline on desktop, below the hero on tablets and below the login form on phones; if it cannot be loaded, the login still works and the box shows a quiet note.

Two unauthenticated, read-only, GET-only routes serve it. They run before the session is started, so they set no cookie and need no CSRF token; other methods get `405`, unknown, draft or past tournaments `404`. Successful responses are `Cache-Control: public, max-age=60`. Every public field is defined in `backend/src/GuestView.php` (mirrored for the demo by `dist/guest-view.js`), and `Repository::guestTournaments()` reads only tournaments that may be public (never accounts or the athlete database):

- `api/index.php?route=public` returns `{tournaments:[{id,name,date,city,status}]}`: tournaments that are not drafts (`open`, `closed`, `finished`) dated today or later in Europe/Warsaw, sorted by date, at most 6.
- `api/index.php?route=public-tournament&id=…` returns, for such a tournament only: the same five fields; `summary` `{entries,clubs,categories,brackets}` (counts); `categories` `[{code,event,type,title,subtitle,gradeType,athletes,state,bracket}]`, where `athletes` is a count and `state` is `pending`, `drawn`, `progress`, `finished`, `underfilled` or `list`; and for a saved draw `bracket` `{size,slots:[{initials,club}|null],results:{matchId:slotIndex}}`.
- Athletes appear only inside saved brackets and only as **initials and club name**. Initials are made on the server (the API never sends a full name): the first letter of the first word and of the last word of the name, each followed by a dot (`Jan Kowalski` → `J. K.`, `Anna Maria Kowalska` → `A. K.`); a hyphenated surname keeps each part (`Kowalska-Nowak` → `K.-N.`); a one-word name gives one letter; diacritics are kept (`Łukasz Żak` → `Ł. Ż.`); leading punctuation is skipped.
- Never public: full names, birth dates, ages, weights, heights, athletes' grades, check-in or presence, champion flags, e-mail addresses, accounts, password hashes, entry/profile/club/user ids, tournament creators and mats, activity, revisions, draft or past tournaments, start lists of points events.

`tests/workspace.test.mjs` and `tests/php.test.mjs` check the allow-list, the initials, the exclusion of drafts and past dates, and that PHP and the demo produce identical output; `tests/http.test.mjs` checks the real API (headers, no cookie, 404/405, no full names, no writes).

To change the advertisement or the encouragement to log in shown in the preview, edit the `AD` and `ACCESS` objects in `dist/promo.js` (Polish text; English goes to `dist/i18n-en.js`, and `tests/i18n.test.mjs` fails until it is there). The brand in the sample ad, KYORUVO, is invented and labelled as fictional. Only the app's own files may be used (CSP): draw visuals in CSS or inline SVG, no external images, links or tracking. `ACCESS.kind` (`login`, `paid` or `free`) is chosen at run time from `public-config` (sign-up and billing switches); the `access-cta` action is handled in `dist/account-boot.js`.

### What guests and unpaid people never see (privacy guarantees)

Every public route runs before the session starts (no session file, no `Set-Cookie`) and returns only fields from an allow-list, so a new database column can never leak by accident.

- **Tournaments:** as above (initials and club only; counts instead of lists).
- **Chat:** `backend/src/ChatGuestView.php` sends a message as exactly `{id, r, t, g, c, b}` (id, revision, time, decoration variant, "same author as the previous message", text) and a tombstone as `{id, r, t, g, x}`. No names, initials, user names, public ids, user ids, e-mails, avatars, countries, sports, clubs or roles, no report counts, no text of deleted or hidden messages and no `people` map. Someone who is signed in but has no full access (unpaid) gets the same guest projection, also from `chat-feed`.
- **What `g` and `c` reveal (on purpose):** `g` = HMAC-SHA256(`app_key`, `chatghost|<UTC day>|<channel id>|<user id>`) mod 5, so the messages of one person in one channel on one day share a variant; `c` marks a follow-up from the same author less than 5 minutes later. A guest can therefore group the messages of one person within one channel and day (5 variants shared by all authors), but cannot link them across channels or days and learns no identity. A variant drawn per message would make one conversation look like many people (the readability trade-off of decision D6). The message text itself is public by product decision; the chat tells people not to write personal data of children or phone numbers.
- **Photos:** profile photos are served by PHP only to people with full access and to the owner; guests and unpaid people get `404` (also with a valid `ETag`); photos are not shown in tables, brackets, prints or the hall screen.
- **No personal data in URLs:** member search and user name checks are POST bodies, so nothing lands in the host's access logs.
- **Shared devices:** after logout, a reset from another tab or a 401 the chat module drops people, messages, cursors and drafts (`purgeIdentity`) and the page reloads into the guest view.
- **Deleting an account** anonymises the user row, turns messages into tombstones, removes the profile and photo and deletes the Stripe customer (retried by a job when Stripe is unreachable). Chat messages are kept 365 days, the original text of removed or reported messages 30 days.

## Chat

- **Channels and visibility.** `chat_channels` has four seeded lobby channels (slugs `taekwondo`, `taekwondo-pl`, `karate`, `general`) and one channel per tournament, created lazily. Tournament channels follow the tournament state: drafts have no public chat, an open or closed tournament is readable by guests until the tournament day, the day after the tournament and the archive are readable only by signed-in people (the default answers to P3 and P17), writing ends at 23:59 of the day after the tournament. Admin can set a channel status.
- **Polling, not sockets.** The hosting has 16 PHP processes and no daemons, so long polling, SSE and WebSockets are rejected (plan D1). Every channel has a revision counter `rev`; the client sends its last known `rev` per channel and the server answers `204` when nothing changed (2-4 indexed queries). Guests use `public-chat` (no session, `Cache-Control: public, max-age=2`), members `chat-feed` (read-only session via `Auth::peek`: no session write beyond the idle/4 activity refresh, no file, no cookie; PHP's files handler still holds the session file lock while it reads; `private, no-store`). Background counters (`h=`) and history (`before=`) share the same request. The client (`dist/chat-transport.js`) runs one poller per browser (Web Locks + BroadcastChannel; the leader tab broadcasts), pauses in background tabs, counts idle time only from the user's own interaction, grows the interval 2.5 s → 5 → 10 → 30 → 60 s, backs off with jitter and honours `Retry-After`. The interval table, the on/off switch and the notice come from `chat_settings` (`cv` → `cfg`) and are changed in the Admin's moderation page without a deploy; presets: Normal (2.5 s), Saver (5 s), Emergency (15 s). The client reports 429/503/508 answers of the host (`e=`); the Admin sees the total of the last hour, counted once per reporter (a guest's address or an account), status and minute, with at most 10 answers per report.
- **Writing.** `chat-send` (POST, CSRF) checks, in order: payment (402), complete profile, temporary password, mute, chat on. `me.access.block` tells the interface which reason applies. `cid` makes sending idempotent. Limits per person and channel, 1-1000 characters, `Text::clean` strips bidi controls and zero-width characters.
- **Moderation.** Reports with a reason; 3 reports from different people hide a message pending review; Admin can delete, restore, dismiss, mute (time-limited) and change channel status; every action is logged in `chat_mod_log`. Moderator-removed text is kept 30 days, then nulled by the `chat-retention` job.
- **Safe rendering.** Values from the API reach the DOM only through `textContent`, `createTextNode` or the escaping `h` template of `dist/registry.js`; `setHtml` is the only HTML sink and accepts only `SafeHtml`. `tests/xss-scan.test.mjs` fails on `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write` or inline handlers in the feature modules.
- **Later stages (designed, not built).** Stage 2: a static "beacon" file per channel served without PHP; stage 3: an external push service that sends only a signal. Neither is part of this release; see `HANDOFF.md`.

## Payments

- **Hosted pages only.** `backend/src/StripeClient.php` calls the Stripe API with plain cURL (pinned `Stripe-Version`, `Idempotency-Key` on every POST, retries only for interactive calls). Card data never touches the app (PCI SAQ A); the CSP is unchanged. Two prices under lookup keys `matbravo_monthly_pln` and `matbravo_monthly_usd`; the currency follows the country in the profile (Poland → PLN, elsewhere → USD) and the Admin can change it for an account without a running subscription.
- **Correct without webhooks.** The host answers 403 to data-centre addresses, so Stripe's webhooks may never arrive. The subscription state is pulled from Stripe: after Checkout (`billing-confirm`), on the Customer Portal return, lazily (`BillingSync::lazy`, after the response, at most every `billing_sync_min_interval` seconds per account), by the jobs `billing-due` and `billing-events`, and by the CLI `bin/stripe-sync.php`. `stripe-webhook` is an optional accelerator: with no `stripe_webhook_secrets` it answers 404; events are verified by `StripeSignature` (HMAC, ±300 s) and processed once (`stripe_events`). When one customer has several subscriptions, a precedence rule keeps the best one in the single `billing_accounts` row. After a network error or a 5xx the background syncs pause (`stripe_down_seconds`).
- **Access state machine.** `backend/src/Access.php` (`Access::compute`, a pure function) turns the billing row, the role and the config into `{full, state, until}`: `open` (payments not enforced), `staff` (Admin), `free`, `active`, `ending`, `past_due` (7 days of grace), `grace` (7 days after a free period), `processing`, `ended`, `none`. Full access is needed to write in the chat, to appear with an identity and to change the tournament workspace. Staff without full access keep read-only access to the workspace and can change the password (`command` answers 402); plain members have no workspace at all, and an organizer's tools need full access in paid mode (402), while withdrawing and correcting an own athlete entry and deleting own data always work.
- **Existing accounts.** Migration 0002 marks all existing admin/editor/club accounts as free (`grandfathered`) so that enabling payments never cuts a club off on a competition day. The Admin can require payment from a chosen date (at least 14 days ahead; banner, then 7 days of grace). New staff accounts created by the Admin are paid unless "Free account" is ticked; the Admin's own role never pays.
- **Tools.** `bin/stripe-setup.php --mode=test|live` (product, prices, portal configuration; asks for the full key with echo off, refuses a key in `argv`, never stores it, prints the config block), `bin/stripe-sync.php` (`--events --due`, `--reconcile`, `--user=ID`, `--dry-run`). The test double `tests/stubs/stripe-stub.mjs` plays Stripe locally.

## Sign-up modes (`app_settings`, panel "Ustawienia")

- **Where it lives.** One versioned row `app_settings(id=1)` (migration 0008, class `backend/src/Settings.php`, modelled on `chat_settings`). Its JSON holds `signup` (`off`/`on`), `payments` (`free`/`paid`), `organizers` (`on`/`paused`), `trustRequired` (bool, default `false`), `supportEmail` and `stripeCheck` (codes only). `normalize()` replaces every invalid value with its default; keys of a later release stay in the JSON; a write with a stale `version` answers 409. There is **no starting row**: until the Administrator saves, `config.php` decides, and on production that means sign-up off and no payments. `config.php` remains the source of the starting values and the emergency ceiling (`signup_force_off`, missing Stripe keys).
- **One place computes what is in force.** `Settings::effective($pdo,$config)` is a pure function over the row (one query by primary key per connection, idempotent, no table gives the values of the file alone). It is called only where its docblock says: `Routes::dispatch` (session, upload and peek-with-cookie routes and routes flagged `settings`), `index.php` and the jobs. `RouteContext::$config` therefore already holds the effective values and `RouteContext::$file` the raw file (only `diagnostics` shows the source). `tests/settings.test.mjs` fails when code outside the allowed files reads `billing_enforce`, `signup_enabled`, `support_email` or `organizers` from a raw config.
- **What the owner sees.** Three modes: *Wyłączona* (off), *Otwarta, bezpłatna* (`signup=on, payments=free`) and *Otwarta, płatna* (`signup=on, payments=paid`); with sign-up off a separate switch controls the payments of existing accounts. Effective values: `signup_enabled = signup 'on' and no signup_force_off`; `billing_enforce = payments 'paid'`; when `paid` is saved but `billing_enabled` is gone from the file, `billing_enforce=false`, sign-up is closed and `settings_degraded='billing-missing'` (registration fails closed, access fails open); `signup_force_off` over a saved `on` gives `settings_degraded='force-off'`; `signup_mode` is `off|free|paid`.
- **Switching to *paid*** (`admin-settings-save`; payments going from `free` to `paid`, the paid sign-up opening, also `off` → `on` while payments are already `paid`, and an unchanged save while `paid` payments are paused (`stripe-check`), run the steps below, the gate): version check; `billing_enabled` must be true (409 `stripe_not_ready`); a Stripe check outside any transaction (`Billing::resolvePrice` for every currency, the price amount equal to `billing_amounts` or 409 with error `amount_mismatch`, recorded in `stripeCheck` with an HMAC fingerprint of the Stripe configuration: mode, key hash, price keys, amounts); test mode needs `allowTestMode` (or the older `confirmTestMode`; otherwise 409 `test_mode` with `confirmTestMode:true`); then, when somebody may lose access he really had (payments start, were never confirmed in the panel: `billing_enforce` from `config.php` alone, or change Stripe mode against the confirmed one: test subscribers on live keys), the decision about the accounts of the free period (409 `free_period_decision` with the counts) from `Billing::freePeriodSet`: group A are the accounts created while sign-up was free (`billing_exempt`, reason `free-signup`), group B those that would lose access at once under payments (`Access::compute` with `billing_enforce=true`, without accounts that already have a subscription of the current mode or were marked paid by the Administrator, so B is empty once payments are already required; with payments already `paid`, a resume after a pause, a change of Stripe mode or payments from `config.php` alone, only accounts that had full access while payments were required, e.g. test subscribers on live keys, never those behind the paywall). The answer is `keep` (everybody stays free) or `requireFrom` (a date at least 14 days ahead; banner, then 7 days of grace). The gate stores the configuration it confirmed (`armed`: fingerprint and mode). Switching back to *free* is always allowed; running subscriptions keep renewing. Once a check or a confirmation is stored, `Settings::effective` runs the paid mode only while the check passed against the current configuration and that configuration is the confirmed one: a failed "Sprawdź Stripe" or a change of the Stripe keys, mode, prices or amounts in `config.php` closes the sign-up and lifts enforcement (`settings_degraded='stripe-check'`; `admin-settings` gives `stripeCheck {ok, stale, checkedAt, mode, rearm}`). A fresh passing check (admin-stripe-check) resumes payments for the confirmed configuration and for a changed one in the same Stripe mode (a rotated key, new price keys or amounts: it becomes the confirmed one, nobody loses access); after a change of mode (test → live keys) or with nothing confirmed it only reports `rearm:true`, and the gate (an unchanged save: in the panel "Zapisz tryb rejestracji" goes to the server without changes while `paid` payments are paused, and the panel names that save when `rearm` is true) resumes them with the test-mode confirmation and the free-period decision. An unchanged save in the confirmed mode resumes them without either question. A check that fails because Stripe is unavailable (network, 5xx) or with another non-definitive error never replaces a passing check of the current configuration, so it never pauses payments.
- **Organizers.** `organizers: paused` stops *unconfirmed* organizers from publishing new tournaments (already published ones and confirmed organizers are not affected). `trustRequired` (plan section 17, **default `false` = full automation**) decides whether an organizer must first be confirmed by the Administrator; with `false` every non-blocked organizer counts as confirmed, so pausing stops nobody. It is read only through `Settings::effective` / `Settings::flags` in `Domain` and in the JS mirror (`db.flags`).
- **Audit and history.** Every save writes `account_audit` (`settings.save`, `settings.support` with old and new value). The panel's history lists the last 50 entries of `settings.*`, `organizer.*`, `club.*`, `tournament.hide` and `profile.forget`, without e-mail addresses.
- **Routes** (`backend/routes/settings.php`): `admin-settings` (GET, peek, admin), `admin-settings-save` (POST, admin), `admin-stripe-check` (POST, admin, 6 per hour). `public-config` returns `signup`, `signupMode`, `billing`, `amounts`, `avatars`, `support` and `roles:true`; `diagnostics` adds `settings:{mode,degraded,version,source}`.
- **Support address.** The default is `hello@matbravo.com` (an empty or invalid value is refused with 422). It is in force from the deploy on whenever neither `config.php` nor the panel names another address: `Settings::effective()` fills `support_email` even without a row, `public-config` returns it, and the existing "Nie pamiętasz hasła?" help panel of the login screen shows it (before this release it showed only the generic "contact the tournament Administrator" text). The mailbox therefore has to exist before the release is merged (`HANDOFF.md`).

## Roles, organizers and athlete self-entry

**Model.** A role is not a value of `users.role`. Everybody who signs up is a `member`; `admin`, `editor` and `club` stay staff. On top of `member`:

- **Organizer** = `role='member' AND users.organizer=1 AND organizer_blocked_at IS NULL`. The person switches it on and off (at sign-up or in the profile tab "Role"); switching it off is refused while one of their tournaments is `open` or `closed`; the Administrator can block it (`organizer_blocked_at`) and confirm the person (`organizer_trusted_at`, `organizer_trusted_by`).
- **Athlete** = at least one non-archived row in `profiles` with `owner_user_id` = the account. `ATHLETES_PER_ACCOUNT = 1` (owner decision, plan section 17; the data model still allows several profiles, the constant and the server validation enforce one); the profile is *self* ("Siebie") or *guardian* ("Moje dziecko lub podopiecznego"). A *self* profile of someone younger than 16 (`MINOR_SELF_AGE`) is refused without a hint of a workaround.
- A person can be both. `me` and the session answers carry `user.caps = {organizer, organizerBlocked, organizerTrusted, athlete}`. Staff accounts get no member capabilities.

**Organizer scope (privacy limit, plan R6).** An organizer sees and runs only **own tournaments**, their entries and **the athletes they added themselves** (plus the profile of their own account). In other people's open tournaments with self-entry they see only **their own entries** (no draws, no log). They never see the athlete database, other organizers' tournaments, athletes' accounts or other people's entries. Staff (editor, club) keep their current view of staff data and see community tournaments only when the organizer counts as trusted and only their own entries. `Domain::publicData` (mirror `publicWorkspace` in `dist/workspace.js`) implements the matrix of plan section 5.2. `Repository::organizerSnapshot()` loads only what an organizer may see, so other children's data does not even reach the request's memory; a test proves `publicData(organizerSnapshot) == publicData(load())` for that organizer.

**How an organizer enters the workspace.** `Actors::of()` builds the member as a workspace account; `Repository::transaction($fn,$actor)` adds it to `$db['users']` for the request only and removes it before saving; `Repository::rows()` always skips members; `persist()` inserts new rows with a plain `INSERT` and updates changed ones with `UPDATE ... WHERE key` (never an upsert; error 1062 on `clubs` becomes 409 "Klub o podobnej nazwie już istnieje"). Command types a member may send are `Domain::ORGANIZER_TYPES` (`tournament.save`, `profile.save|archive|forget`, `entry.save|remove`, `checkin.save`, `draw.create`, `result.save|clear`); anything else is 403. The tools need the **password again** after 30 minutes without use and at least every 12 hours (`ws:{at,last}` in the session; 401 `code:'reauth'`; `organizer-unlock` re-checks the password; the client opens a password dialog and repeats the request once). Chat, profile, "Moje starty" and the `athlete-*` routes do not need it.

**Limits** (constants in `Domain` and `dist/workspace.js`). `ORGANIZER_DAY=3` new tournaments per 24 h (drafts count), `ORGANIZER_ACTIVE=10` published upcoming ones (drafts and hidden ones do not count), `COMMUNITY_DAY_GLOBAL=50` new tournaments per day from unconfirmed organizers together, `ORGANIZER_PROFILES_DAY=300`, `CLUBS_DAY_PER_USER=3`, `CLUBS_DAY_GLOBAL=30` (past the limit the club becomes "Niezrzeszony" with a pending name for the Administrator), `ADULT_AGE=18`, `RETENTION_MONTHS=24`. The status "finished" is possible only from the tournament day. Texts of members pass `Text::clean` and `Domain::CONTACT` (no web addresses, e-mail addresses or long numbers). Per-account rate limits and a global bucket of 120 member transactions per minute (staff never waits for it) live in `index.php` and `backend/routes/athletes.php`. A profile of someone under 16 added by an organizer needs the guardian declaration (`guardianConsent`); the consent texts themselves are empty slots for the legal session.

**Trusted organizers.** With `trustRequired=true` a tournament of an unconfirmed organizer is public only under its own address (`#guest?t=...`) and on the athlete's open list (with a badge); it is not on the home page or in the chat lobby, and people under 18 cannot enter it by themselves. Confirmed organizers are also exempt from the global limit and from `organizers: paused`. With the default `trustRequired=false` every non-blocked organizer behaves like a confirmed one. The Administrator confirms, blocks (optionally hiding upcoming tournaments and withdrawing self-entries) and bulk-blocks in "Członkowie", hides or restores a tournament with a reason from the tournament card, and manages clubs in "Kluby" (verify, rename, merge, adopt pending names).

**Clubs.** `clubs` got `verified`, `created_by`, `created_at`, `merged_into`. The club `unaffiliated` ("Niezrzeszony") is created by `Clubs::ensure()` in the first workspace transaction and before a sign-up chooses it, and is never treated as the same club in a draw (`Rules::sameClub`). `Clubs::pick` (pure, shared by `Domain` and sign-up) chooses from the list, creates an unverified club or falls back to "Niezrzeszony"; `Clubs::key` / `clubKey` compare names. `public-clubs` lists verified, unmerged clubs only; unverified names are not public, also not in brackets (`club:null`). The demo clubs of `seed-athletes` are created unverified.

**Athlete self-entry.** A tournament has `tournaments.self_entry` (new tournaments of organizers: on by default; staff: off; existing ones: off; the switch is "Zawodnicy mogą zgłaszać się sami" in the tournament settings). `athlete-entry` runs through `Domain` (`entry.self`) under the workspace lock: the tournament must be `open`, with self-entry on, not hidden and not past, and, for a new entry, its member organizer neither blocked nor deactivated (`Domain::closedCreator`: nobody runs it, so it takes no new entries from outside, also from staff; withdrawals and corrections of entries made earlier work as before, by owners, clubs, editors and other organizers, for a deactivated organizer; blocking also takes away trust, so in a blocked organizer's tournament clubs, editors and other organizers can no longer correct or withdraw, a minor's self-entry cannot be corrected, only owners withdraw (adults also correct) and the Administrator handles the rest); the profile belongs to the account; the target categories must not have a saved draw; a minor can enter a community tournament only when the organizer counts as trusted; the snapshot is built by the same function as a club entry (`self:true`, `champion=false`). In paid mode a new entry needs full access (402), but **withdrawing, correcting an own entry without new events (R12), `athlete-save`, `athlete-forget`, `athlete` and `me` always work**. `athlete-withdraw` is allowed while the tournament is `open` and the category has no draw; when an organizer, the Administrator or the system removes an entry, a tombstone in `entry_withdrawals` is shown on "Moje starty". The athlete page is built by `AthleteView::project` (allow-list; other people only as initials and club; at most `OPEN_LIMIT=50` open tournaments and `ENTRY_LIMIT=100` entries), mirrored by `dist/athlete-view.js`; a parity test compares them. There are no e-mails: statuses are shown on "Moje starty".

**Deleting data.** `Domain::detach` (a finished tournament or a closed one with a saved draw keeps the entry; so does a failing `reconcile`; an erasure by someone who does not manage the tournament, a member organizer or athlete, account deletion, never drops a saved draw of an open tournament either: the entry stays and its profile is anonymised; the snapshot keeps the name only as results history of a tournament that took place (finished or dated before today, O7) and gets initials in an upcoming one, also on account deletion and retention; `profile.forget` and `athlete.forget` always give initials), `Domain::forgetProfile` (delete or anonymise; log lines are matched by `profileId`), `Domain::forgetMember` (account deletion: profiles forgotten, upcoming tournaments of an organizer hidden by `system`), `Domain::retain` (job `community-retention`, once a day: organizer-created profiles whose last tournament is older than 24 months are forgotten, names in community tournaments become initials, old tombstones are purged). `accounts-cleanup` never removes an account that holds community data. `seed-athletes --remove` refuses while a demo club holds a community profile.

**Revisions.** `app_meta.revision` stays the lock and the version number, but a command is refused as stale only when the objects it touches changed (`tournaments.rev`, `profiles.rev`, `app_meta.staff_rev`; `Domain::stale`), so an organizer's or an athlete's write does not invalidate the forms that staff have open at the check-in desk. `bootstrap?t=<id>&rev=<n>` answers `{unchanged:true}` after one query (the hall screen polls it).

**Routes added in this release** (`backend/routes/accounts.php`, `athletes.php`, `settings.php`): `roles` and `organizer-unlock` (members); `public-clubs` (public); `athlete`, `athlete-save`, `athlete-archive`, `athlete-forget`, `athlete-entry`, `athlete-withdraw` (members); `admin-settings`, `admin-settings-save`, `admin-stripe-check` (admin). Changed: `signup` (body `roles{organizer,athlete}` and `athlete{...}`, validated before any transaction and without the workspace lock), `me`, `public-config`, `admin-members` (filters, `ownerOf`), `admin-member` (actions `organizer`, `organizer-trust`, `organizer-bulk`), `bootstrap`, `command`, `diagnostics`.

**Frontend modules** (all plug into the registry): `account-flow.js` / `account-boot.js` (sign-up with roles, the athlete step, landing after sign-up, the tab "Role"), `athlete-form.js`, `club-picker.js` (radio group plus ARIA combobox), `athlete-boot.js` / `athlete-flow.js` / `athlete-data.js` / `athlete-view.js` ("Moje starty", the entry window, the call to action in the member preview), `admin-settings.js`, `admin-clubs.js`, `admin-members.js` (badges, filters, trust, bulk block), `settings-boot.js`, and organizer behaviour in `app.js` (own tournaments only, copy link, club check at check-in, password dialog). In the static demo the organizer and athlete are demo accounts; sign-up, settings and server actions of the Administrator answer "Ta funkcja jest niedostępna w wersji demonstracyjnej."

**Chat lobby and brand details of this release.** Migration 0009 only sets `chat_channels.sort`: Taekwondo Polska first, then Taekwondo (world), Karate and General; `Chat::LOBBY` carries the same order. World channels show `dist/brand/globe.svg`. On screens wider than 1760 px the home page stays centred (`dist/workspace.css`).

## Architecture

### Frontend

`dist/client.js` chooses the demo or API adapter via `runtime-config.js`. The PHP package selects `mode:'api'`. `workspace.js` models demo commands; `backend/src/Domain.php` enforces production commands. `Rules.php` independently validates and resolves brackets. `dist/app.js` stays the shell of the tournament workspace; every other feature is a module that plugs into the registry `dist/registry.js` (no imports, so no cycles): `registerPage`, `registerPublicPage`, `registerAction`, menu items, badges, events and the safe HTML template `h`. `app.js` has one-time hooks for it. Hash routes (`#chat`, `#signup`, `#profile`, `#billing`, `#members`, `#moderation`, `#tournaments`, …) are parsed by the registry; `#screen` (hall screen) and `#guest` (public preview) are never touched by the PWA layer. A registry page that throws or returns a plain string is logged and replaced by the built-in page. Feature modules: `chat-*.js` (+ `chat.css`), `account-*.js`, `avatar-crop.js`, `profile-data.js` (rules shared with PHP), `admin-members.js`, `chat-admin.js`, `pwa.js`, `me.js` (the signed-in person's community state from the `me` route), each with a small static `*-boot.js` and its own CSS and English dictionary; the heavy screens load on demand.

### Backend

- **Front controller** `backend/public/api/index.php` serves the original routes (`session`, `bootstrap`, `login`, `logout`, `command`, `public`, `public-tournament`). **Route registry** `backend/routes/*.php` (`core`, `accounts`, `athletes`, `billing`, `chat`, `settings`) defines every other route with an access mode: `public` (GET, no session, no cookie), `peek` (GET, read-only session: no session write beyond the idle/4 activity refresh, no file, no cookie; the files handler still holds the session file lock while it reads), `session` (POST: Origin and CSRF check, JSON body with a size limit), `upload` (raw body with a content type), `webhook` (no session, signature checked by the handler), plus the required user kind (`required`, `optional`, `admin`, `member`, `anon`). The user requirement is checked before the handler runs, so an admin route answers 403 before reading anything. Errors: `AppError`/`ApiError` give `{error,csrf,…}`; a missing table or column (code newer than the database) gives 503 "Trwa przerwa techniczna", never 500; anything else gives 500 logged without the PDO message.
- **Jobs** `backend/jobs/*.php` (`housekeeping`, `accounts-cleanup`, `chat-retention`, `billing-due`, `billing-events`, `community-retention`) run without cron: after the response of `me` and `chat-send`, after the session lock is released, claimed with a conditional `UPDATE` of `job_runs`, a few seconds at most. The payment jobs and the lazy payment sync need a SAPI that can send the response early (`fastcgi_finish_request`/`litespeed_finish_request`; `diagnostics` reports it as `server.afterResponse`); without it the `stripe-sync.php --events --due` cron is mandatory. `bin/cron.php` runs the same jobs from cron.
- **Migrations** `backend/migrations/NNNN_name.php` with the version in `app_meta.schema_version`: `schema.sql` is the frozen version 1, `0002_accounts` (role `member`, `user_profiles`, `billing_accounts`, `job_runs`, `account_audit`; existing accounts become free), `0003_chat` (channels, messages, reports, mutes, moderation log, settings, health), `0004_billing` (`stripe_events`, `billing_audit`, `billing_kv`), `0005_staff_index` (index `users_role`: the workspace reads staff without scanning members), `0006_billing_customers` (every Stripe customer an account ever had, so account deletion deletes them all), `0007_roles` (organizer and trust columns on `users`, `profiles.owner_user_id` and `rev`, club verification and merge columns, tournament `created_at`, `hidden_*`, `self_entry` and `rev`, `app_meta.staff_rev`, table `entry_withdrawals`; **with a floor**: once community data exists, rolling back to older code is refused), `0008_settings` (table `app_settings`, no starting row, no floor) and `0009_lobby_order` (only `chat_channels.sort`, no floor). Migrations only add (a lint test enforces a SQL subset that runs on MariaDB 10.6 and MySQL 8.0), so the previous release keeps working on the new schema; `bin/migrate.php` (`--status`, `--dry-run`, `--rollback-floor`) refuses destructive ones without `--allow-destructive`. `bin/install.php` applies the baseline and every migration, then creates the first Admin. The deploy takes a database copy before migrating; a "floor" guard blocks rolling back to code that does not understand data already stored (for example once members exist).
- **Isolation of members.** `users` stays one table with a new role `member` and a nullable `club_id`. `Repository::load()` never loads members into the tournament workspace, `persist()` writes `users` with explicit `INSERT`/`UPDATE` (never an upsert, which would take over a member's row). A member without the organizer capability gets 403 from `command` and an empty workspace from `bootstrap`; an organizer enters only as the actor of their own request (see "Roles, organizers and athlete self-entry"). Chat, billing and profiles never go through `Repository::transaction()` (the global lock): they use their own tables, indexed queries and a row lock on the channel.
- **Sessions.** Staff 30 min idle / 12 h absolute, members 14 / 30 days (peek routes refresh activity at most once per idle/4: always for a member session; for a staff session only on a `chat-feed` poll that carries `a=1` together with a channel on screen, `Chat::active`, the server side of the plan §3.5 step 6 exception for a club representative who only reads the chat. `dist/chat-transport.js` adds `a=1` to such a poll while the person's own last interaction is within the last idle level, `cfg.idle[3]` (30 min by default), and never to heads-only polls, history pages or the public chat; once a staff member leaves an open chat untouched for that long, the polls stop carrying it and the session expires after its 30 min idle limit like any idle staff tab. Background polls such as the chat heads or the moderation badge never keep an unattended staff tab signed in; otherwise staff activity is a session request), in the app's own directory `~/matdraw/shared/sessions`; the `housekeeping` job removes files by kind (anonymous 3 h, staff 12 h, members 14 days). `Accounts::current` is lightweight (no transaction, no global lock) and a guest without a cookie never opens a database connection. Login takes the same time for known and unknown e-mails (dummy hash with the same parameters as `Domain::password`).
- **Rate limits** (`RateLimit`, HMAC buckets in `login_limits`, IPv6 grouped by /64): login (IP and IP + e-mail), sign-up (IP per hour and day, global per hour), user name checks, profile, password, photo, chat sending, reports, the Stripe probe. Defaults are raised for a sports hall where many phones share one IP.
- **Original design (unchanged).** Tables normalize ownership and foreign keys; profile attributes, entry snapshots and draw payloads are JSON. Repository transactions hold `app_meta` via `SELECT ... FOR UPDATE`, compare a revision, then persist changed records. Reads use a consistent transaction. Optimistic revision checking prevents stale overwrites and duplicate retried writes.

Auth uses secure HttpOnly SameSite cookies, CSRF for all writes, login throttling, idle/absolute expiry and session revocation after role/club/email/password changes or blocking. Apart from the public schedule, the guest preview and the public chat described above, every read requires a session. Self-service sign-up exists but is off until the Administrator opens it in "Ustawienia" (or, as a starting value, `signup_enabled` in `config.php`); there is still no e-mail delivery, no automatic password recovery, no judge role and no unauthenticated projector token. Staff passwords are reset by the Admin in "Konta i role"; a member's password is reset by the Admin as a one-time temporary password after a request from the account's own address (procedure in `HANDOFF.md`), and the member must change it at the next login. The last active admin cannot be disabled or demoted.

The workspace of the tournaments still loads whole and writes are globally serialized. It is intended for small/medium tournaments; large histories need pagination and per-aggregate revisions. Tournament activity is a bounded list of 40 changes, not a full audit ledger. Rules are not versioned per tournament in this release; changes to the rule engine require explicit migration planning for historical categories.

## Rule limitations

No bronze-medal rule is silently selected. Ambiguous female Cup light-contact and younger female semi-contact weight categories remain blocked. Age 45 in split veteran groups is blocked. Date-of-birth age is calculated on tournament day and needs coach approval. Younger Dan eligibility, 200 g tolerance semantics, decimal boundaries, soft/kalaki equivalence, >16 placement and points-list format need coach confirmation. Draws support 3–64 entrants; heuristics reduce club collisions but do not guarantee an optimum. See `dist/architecture.html` and the app's rules page.
